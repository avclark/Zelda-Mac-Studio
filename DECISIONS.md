# Engineering decisions

- Sonoma 14 deployment target; Xcode 16.2 / Swift 6.0.3 in Swift 5 language mode. Native SwiftUI UI and Foundation/CryptoKit core. No downloaded dependencies.
- Local schema-versioned JSON catalog references immutable environment revisions. Each change stages a new revision; a single atomic catalog replacement commits it. Snapshots retain old revisions. A failed commit leaves the prior catalog valid and staged data unreferenced. No destructive garbage collection in v1.
- Every clone has copied save and overlay files under a new environment UUID. No shared mutable runtime directories. No direct access to existing emulator state.
- ZIP support uses a strict parser plus the macOS system zlib for bounded decompression and CRC verification. Unsupported ZIP features fail closed. Folder imports reject links and special files.
- A local laboratory deployer is useful for verifiable overlay workflows. It does not pretend to launch a game. Runtime adapters must remain unavailable until their isolation and real prerequisites are verified.
- File-level copies preserve empty directories and never use hard links. Managed path ancestry is checked for symlinks. ZIP CRC and expanded-size checks complement SHA-256 manifests. Case/Unicode collisions are conservatively blocked even on case-sensitive volumes.
- Snapshot restore is a new revision plus an atomic pointer/catalog update, not an in-place file swap. Failure injection proves prior committed state remains active. Old revisions/stages are retained for manual recovery; pruning is deferred. Power-loss durability is not claimed.
- Portable exports are new immutable directories. Import of an existing identity always creates a branch. This intentionally favors preserving saves over deduplicating repeated pulls. Save export is opt-in; the implementation only writes local filesystem folders.
- Local references use security-scoped bookmarks in app preferences and are excluded from exports. Registration does not imply game integrity validation. The known damaged base remains blocked; no "trust anyway" path exists.
- The Xcode app project links StudioCore through a local Swift package. AppKit supplies macOS pickers, bookmark access and a generated original icon. The app is not App Sandbox-distributed/notarized; no permissions or security settings are changed by setup.
- App filesystem tasks run on one serial worker queue; the UI gets value snapshots on the main thread. The core also locks and reloads on each mutation so separate instances do not overwrite unseen committed environments. Deploy rejects a configuration changed after preview.
- Runtime integration is deliberately gated, not simulated. Current native, emulator and merge research is in Docs/UPSTREAM.md. Core owned-process tests use system sleep; that is not proof of game launch.
